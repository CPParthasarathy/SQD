# C1.2 Component Interface and Runtime Contracts

## Purpose

C1.2 converts the accepted C1.1 system architecture into explicit
component-interface and runtime contracts.

The governing completion criterion is:

> Every mutable resource and interface has a single owner.

This document defines:

- Public API ownership and naming.
- Mutable-resource ownership.
- Input, output, memory and lifetime rules.
- Threading and concurrency boundaries.
- Initialization, start, stop and deinitialization semantics.
- Cross-component error classification and propagation.
- Permitted dependency directions.
- Machine-checkable requirements for later verification.

## Scope

### In scope

C1.2 covers the interface and runtime boundaries for:

- `main/`.
- `components/app`.
- `components/domain`.
- `components/connectivity`.
- `components/update`.
- `components/platform`.
- `components/services`.
- `components/storage`.
- `components/security`.
- `components/diagnostics`.
- `components/device_drivers`.
- `components/hal`.
- `components/board`.
- `components/build_metadata`.

Existing and planned components are included. A planned component contract
becomes binding when that component is implemented.

### Out of scope

The following remain assigned to later work packages:

- Architecture exceptions and lateral dependencies: C1.3.
- Exact board pins and electrical details: C2.1.
- HAL and device-driver implementation: C3.
- Complete startup, shutdown and safe-mode policy: C5.
- Task priorities, stack sizes, queue depths and watchdog budgets: C6.
- Detailed storage, diagnostic and security implementation: C7 and C8.

## Global Interface Rules

1. Every public interface has exactly one owning component.
2. Every mutable resource has exactly one owning component.
3. Public symbols use the `sqd_` namespace.
4. Component APIs use the `sqd_<component>_` prefix.
5. Only the owning component defines symbols in its namespace.
6. Dependencies are passed explicitly during initialization.
7. Hidden dependency lookup through unrelated globals or singletons is prohibited.
8. Mutable component state remains private to the owning component.
9. Callers receive values, capabilities or opaque handles rather than native
   implementation handles.
10. Caller-owned buffers remain caller-owned unless ownership transfer is
    explicitly documented.
11. A successful ownership transfer leaves exactly one owner.
12. A failed ownership transfer leaves ownership with the caller.
13. Heap ownership does not cross a component boundary without an explicit
    release operation.
14. The component that allocates an object owns its release operation.
15. Input pointers, ranges, state and configuration are validated before
    owned state is modified.
16. Public interfaces do not expose ESP-IDF peripheral handles, FreeRTOS
    object handles, peripheral registers or board pin numbers.
17. Native ESP-IDF errors are translated at the owning component boundary.
18. Same-level component dependencies require an approved C1.3 architecture
    decision.
19. Partial failure leaves the owning component in a documented and
    recoverable state.
20. Public interface changes require specification, ownership and verification
    updates.

## Mutable-Resource Ownership

Only the designated owner may create, mutate, destroy or serialize access
to the resource.

| Mutable resource | Sole owner |
|---|---|
| Product orchestration state | `components/app` |
| Domain model and product-rule state | `components/domain` |
| Connectivity session and protocol state | `components/connectivity` |
| Active OTA transaction state | `components/update` |
| Platform capability registry | `components/platform` |
| Service registry and lifecycle state | `components/services` |
| NVS, filesystem and persistent transaction handles | `components/storage` |
| Credential and cryptographic runtime state | `components/security` |
| Fault ring, health snapshot and diagnostic counters | `components/diagnostics` |
| Device-instance and device-protocol state | `components/device_drivers` |
| Peripheral handles, interrupt bindings and bus locks | `components/hal` |
| Board detection and safe-preparation state | `components/board` |

Non-owners request operations through the owner's public interface.
They must not directly lock, modify, release or expose the owner's resource.

## Memory and Lifetime Rules

1. Configuration objects are read during initialization unless a longer
   lifetime is explicitly documented.
2. Dependency tables remain valid for the component-context lifetime or
   are copied by the receiving component.
3. Mutable component state remains behind an opaque context.
4. Opaque contexts are created and destroyed only by their owning component.
5. Caller-owned buffers remain owned by the caller unless transfer is
   explicitly documented.
6. A successful transfer leaves exactly one owner.
7. A failed transfer leaves ownership with the caller.
8. Asynchronous operations copy submitted data or explicitly accept
   ownership transfer.
9. Returned internal views are read-only and valid only for their documented
   lifetime.
10. Callback event data is valid only for the duration documented by the
    interface owner.
11. Transient callback pointers must not be retained.
12. The component that allocates an object provides its release operation.
13. Secret material must not be returned through logging or diagnostic
    interfaces.

## Threading and Concurrency

Components are passive by default.

A passive component:

- Creates no task.
- Owns no unregistered worker.
- Executes in the caller's context.
- Serializes access to its mutable resources.
- Documents whether each public operation may block.

Active execution is permitted only through the controlled service-supervision
model.

| Component | Execution model |
|---|---|
| `main/` | Composition root |
| `components/app` | Supervised active coordinator |
| `components/domain` | Passive |
| `components/connectivity` | Supervised state machine |
| `components/update` | Supervised state machine |
| `components/platform` | Passive |
| `components/services` | Supervisor-owned workers |
| `components/storage` | Passive and serialized |
| `components/security` | Passive and serialized |
| `components/diagnostics` | Passive with bounded non-blocking ingress |
| `components/device_drivers` | Passive and owner-serialized |
| `components/hal` | Passive with controlled interrupt boundary |
| `components/board` | Passive |
| `components/build_metadata` | Immutable and read-only |

Task priorities, stack sizes, queue depths, timers and watchdog budgets
remain assigned to C6.

### Interrupt context

Only the HAL or board boundary may register native interrupt handlers.

An interrupt handler may:

- Capture minimal hardware state.
- Clear the interrupt source.
- Submit a bounded notification to deferred execution.

An interrupt handler must not:

- Allocate memory.
- Block.
- Access persistent storage.
- Invoke product policy.
- Produce unbounded logging.
- Call an API not explicitly marked interrupt-safe.

## Lifecycle Contract

The standard component lifecycle states are:

- `UNINITIALIZED`
- `INITIALIZED`
- `STARTING`
- `RUNNING`
- `STOPPING`
- `STOPPED`
- `FAULTED`

A component uses only the states applicable to its execution model.

### Initialization

Initialization must:

- Validate configuration and dependency inputs.
- Establish only resources owned by the component.
- Avoid hidden dependency lookup.
- Avoid starting unregistered background work.
- Roll back partially created resources if initialization fails.
- Return `SQD_STATUS_ALREADY_INITIALIZED` for repeated compatible initialization
  when initialization is not implemented as fully idempotent.
- Return `SQD_STATUS_INVALID_STATE` for conflicting initialization.

### Start

Start applies only to active components.

Start must:

- Require successful initialization.
- Enter `STARTING` before activation.
- Return success only when contracted work can be accepted.
- Enter `RUNNING` after successful activation.
- Release or roll back partially activated resources after failure.

### Stop

Stop must:

- Reject or control new work according to the component contract.
- Complete, cancel or return pending owned work deterministically.
- Preserve persistent-data consistency.
- Complete within a documented timeout.
- Leave the component in `STOPPED` or `FAULTED`.

### Deinitialization

Deinitialization must:

- Occur only after active work has stopped.
- Release resources owned by the component.
- Never release caller-owned dependencies.
- Return the component to `UNINITIALIZED`.

The complete system initialization order, reverse shutdown order and
safe-mode escalation policy remain assigned to C5.

## Error Contract

Cross-component interfaces use `sqd_status_t`.

Required status classes are:

- `SQD_STATUS_OK`
- `SQD_STATUS_INVALID_ARGUMENT`
- `SQD_STATUS_INVALID_STATE`
- `SQD_STATUS_ALREADY_INITIALIZED`
- `SQD_STATUS_NOT_FOUND`
- `SQD_STATUS_BUSY`
- `SQD_STATUS_TIMEOUT`
- `SQD_STATUS_IO`
- `SQD_STATUS_INTEGRITY`
- `SQD_STATUS_AUTHORIZATION`
- `SQD_STATUS_NO_MEMORY`
- `SQD_STATUS_NOT_SUPPORTED`
- `SQD_STATUS_CANCELLED`
- `SQD_STATUS_INTERNAL`

Error-handling rules:

1. Success is represented only by `SQD_STATUS_OK`.
2. Native ESP-IDF errors are translated at the owning component boundary.
3. Product-level components must not receive `esp_err_t`.
4. Invalid arguments are rejected before owned state is modified.
5. Timeout and cancellation are distinct outcomes.
6. Authorization failure is not reported as generic I/O failure.
7. Integrity failure is not silently converted into not-found.
8. An owner either handles an error completely or propagates it.
9. Silently logging an error and continuing is prohibited.
10. Error reporting must not disclose credentials or secret material.
11. Retry policy belongs to the caller or product-policy owner.
12. Fatality, degraded operation and safe-mode escalation remain assigned
    to C5.

## Dependency Contract

The accepted C1.1 dependency direction remains binding.

Additional C1.2 rules are:

1. A caller depends on the public interface of the owning component.
2. A caller must not depend on another component's private implementation.
3. Dependencies are declared explicitly during initialization or composition.
4. Product components may consume product-service and platform-service interfaces.
5. Platform services may consume device-driver and HAL interfaces.
6. Device drivers may consume HAL and board interfaces.
7. HAL may consume board facts and approved ESP-IDF peripheral facilities.
8. Board may consume approved ESP-IDF foundation facilities.
9. `components/build_metadata` remains an immutable cross-cutting leaf.
10. Native dependency handles must not be passed upward across ownership boundaries.
11. Upward dependencies are prohibited.
12. Same-level dependencies require an approved C1.3 architecture decision.
13. This document approves no same-level dependency exception.

Permitted dependency summary:

| Caller | Permitted dependency targets |
|---|---|
| `main/` | `components/app`, `components/build_metadata` |
| Product application and product services | Product services and platform services |
| Platform services | Device drivers and HAL |
| Device drivers | HAL and board |
| HAL | Board and approved ESP-IDF peripheral facilities |
| Board | Approved ESP-IDF foundation facilities |
| Build metadata | No SQD component dependency |

A component must not transfer ownership of its native dependency handle
to a higher layer.

## Acceptance Criteria

C1.2 is ready for architecture review when:

1. Every controlled component has exactly one API owner.
2. Every mutable resource has exactly one owner.
3. No mutable resource is assigned to multiple owners.
4. Memory-transfer and object-lifetime rules are explicit.
5. Every component has a defined execution model.
6. Unregistered task creation is prohibited.
7. Interrupt-context restrictions are explicit.
8. Lifecycle states and operation semantics are defined.
9. Cross-component error classes and propagation rules are defined.
10. Native ESP-IDF, FreeRTOS and peripheral handles do not escape their
    owning boundary.
11. Upward dependencies are prohibited.
12. Same-level dependencies are absent or approved by C1.3.
13. A machine-readable ownership contract exists.
14. Static verification and negative tests pass.
15. Pull-request and post-merge CI pipelines pass.

The governing completion criterion remains:

> Every mutable resource and interface has a single owner.
