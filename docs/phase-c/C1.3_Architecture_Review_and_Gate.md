# C1.3 Architecture Review and Cluster C1 Gate

## Purpose

C1.3 closes Cluster C1 by reviewing the accepted C1.1 architecture and
the accepted C1.2 component-interface and runtime contract as one
controlled architecture baseline.

The governing completion criterion is:

> No circular dependencies or overlapping responsibilities remain.

C1.3 must demonstrate that:

- The machine-readable architecture graph matches accepted C1.1 and C1.2.
- Every dependency target resolves to one controlled component.
- The complete permitted-dependency graph is acyclic.
- Dependency direction is downward.
- Same-level dependencies are absent or explicitly approved.
- Every mutable resource has exactly one owner.
- Planned components are represented without being treated as existing
  repository directories.
- The Cluster C1 gate remains closed until current verification and review
  evidence pass.

## Governing baseline

The source-of-truth order is:

1. `docs/phase-c/C1.1_System_Architecture.md`
2. `docs/phase-c/C1.2_Component_Interface_and_Runtime_Contracts.md`
3. `tools/ci/c1_2_component_contract.json`
4. `tools/ci/c1_architecture_contract.json`

The C1.3 architecture contract is derived from the accepted C1.2
machine-readable contract. It must not independently redefine component
identity, ownership, layer placement or permitted dependencies.

## Controlled component model

The reviewed component model contains 14 records:

- Composition root: `main`
- Product application: `app`
- Product services: `domain`, `connectivity`, `update`
- Platform services: `platform`, `services`, `storage`, `security`,
  `diagnostics`
- Hardware-abstraction device-driver sublayer: `device_drivers`
- Hardware-abstraction generic-HAL sublayer: `hal`
- Board and hardware foundation: `board`
- Controlled cross-cutting leaf: `build_metadata`

`board` is the sole board-support component. A separate `bsp` component
or directory is not part of the accepted architecture.

Planned components remain valid architecture records:

- `domain`
- `device_drivers`
- `hal`

Their planned status does not permit them to be omitted from ownership or
dependency review.

## Dependency review decisions

The complete accepted C1.2 permitted-dependency allowlist is reviewed
conservatively as the architecture graph.

The following rules govern the graph:

- Composition root dependencies point to product application or immutable
  build metadata.
- Product application dependencies point to product services.
- Product-service dependencies point to platform services.
- Platform-service dependencies point to device drivers or generic HAL.
- Device-driver dependencies point to generic HAL or board.
- Generic HAL dependencies point to board.
- Board and build metadata have no SQD component dependencies.
- Upward dependencies are prohibited.

The device-driver-to-HAL relationship is an ordered dependency between
hardware-abstraction sublayers. It is not a same-level waiver.

## Same-level dependency review

The accepted C1.2 contract contains no approved same-level dependency.

Therefore:

- C1.3 approves no same-level dependency.
- `architecture_decisions` is empty.
- No ADR waiver is required for the current baseline.
- Any future same-level dependency requires a new ADR and a new C1.3-style
  architecture review before implementation.

## Recovered candidate disposition

Preliminary files recovered from protected pre-C1.1 work were reviewed
only as historical candidates.

Two candidate decisions were rejected:

1. Candidate ADR-0001 proposed `diagnostics -> services` and
   `diagnostics -> storage`. These dependencies are absent from accepted
   C1.2.
2. Candidate ADR-0002 treated `platform -> hal` as a same-layer waiver.
   Accepted C1.1 and C1.2 define platform-service-to-HAL as downward and
   device-driver-to-HAL as an ordered hardware-abstraction sublayer
   relationship.

The candidate ADR files are not part of the C1.3 deliverable and must not
be treated as accepted decisions.

The historical verification result dated 2026-07-26 was generated from
the obsolete candidate graph. It is not current C1.3 evidence.

## Machine-readable architecture contract

`tools/ci/c1_architecture_contract.json` is reconstructed directly from
the accepted C1.2 machine-readable contract.

For every controlled component it records:

- Component identifier and repository path.
- Layer identifier and deterministic layer rank.
- Existing or planned implementation status.
- API namespace and execution model.
- Solely owned mutable-resource identifiers.
- Permitted component dependencies.

The contract also records immutable source blob identities so that source
drift can be detected.

## Downstream constraints

C2.1 and all later hardware-facing work must use `board`, not `bsp`, as
the sole board-support identity.

C3 work must retain separate `device_drivers` and `hal` component groups.
Device-specific state belongs to `device_drivers`; generic peripheral
handles, interrupt bindings and bus locks belong to `hal`.

No downstream work may introduce a same-level dependency without a
reviewed architecture decision.
